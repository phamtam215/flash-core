Business

Phase này chưa có nghiệp vụ thật — chưa có API bán hàng nào cả. Mục tiêu duy nhất là dựng nền móng đúng đắn để các phase sau xây lên mà không phải đập đi làm lại. Giống việc đổ móng nhà trước khi xây tầng: không ai "demo" được cái móng, nhưng xây sai móng thì mọi tầng sau đều lệch.

Technical

  • NestJS + TypeScript strict mode, cấu hình đọc qua Zod — sai/thiếu biến môi trường thì app chết ngay lúc khởi động, không phải lỗi mù mờ giữa chừng lúc có khách.
  • Log JSON có cấu trúc (Pino) + correlationId xuyên suốt một request — truy một lỗi qua nhiều dòng log bằng đúng một mã, thay vì đoán mò.
  • Prisma 7 kết nối Postgres qua driver adapter (pg.Pool tự cấu hình) — số connection trở thành một biến nhìn thấy và chỉnh được, quan trọng cho benchmark ở Phase 3.
  • Exception filter thống nhất: mọi lỗi trong toàn app trả về CÙNG một hình dạng response, không phải mỗi endpoint một kiểu.
  • Ranh giới module (xem Q&A #3) — thứ duy nhất khiến kiến trúc này khác một monolith thường.
  • CI: lint + typecheck + test chạy mỗi lần push.

Kiến thức học được (Q&A)

1. Modular Monolith khác Microservices ở đâu?

Cả hai đều là cách chia hệ thống, khác độ tách. Monolith thường: 1 process, không có ranh giới rõ giữa các phần — nhanh viết, nhưng sau vài tháng thành mớ phụ thuộc chằng chịt. Microservices: nhiều service độc lập, mỗi service tự deploy, tự DB riêng — tách được thật, nhưng phải tự xây lại từ đầu mọi thứ một DB đơn lẻ vốn cho sẵn (distributed transaction, service discovery, độ trễ mạng giữa các service). Modular Monolith: MỘT process, MỘT DB, nhưng module có ranh giới được ép bằng máy — giữ được transaction/lock của một DB (thứ Phase 3 cần để chống oversell), mà vẫn có sẵn "đường cắt" nếu sau này thật sự cần tách.

2. Vì sao dự án một người không nên làm microservices?

Với một người, thời gian hữu hạn chảy vào đâu quyết định học được gì. Microservices đòi hỏi cả một tầng hạ tầng: service discovery, distributed tracing, saga pattern cho transaction xuyên service, deploy nhiều service riêng — toàn bộ thời gian đó không dạy gì về concurrency, mục tiêu thật của dự án. Tệ hơn: oversell trong hệ phân tán là bài toán khác hẳn — mất khả năng dùng transaction/lock của một DB duy nhất, tức là mất đúng thứ dự án này muốn học.

3. Ranh giới module được ép bằng gì trong NestJS?

Hai tầng, cả hai đều là máy, không phải quy ước:

  1. NestJS DI container — provider không nằm trong exports của module thì module khác không inject được. Nhưng nó chỉ chặn việc inject, không chặn việc import thẳng file rồi tự new.
  2. ESLint no-restricted-imports — chặn import sâu vào file bên trong module khác, đúng lỗ hổng mà tầng 1 để lọt.

Thiếu tầng 2 thì ranh giới chỉ còn là quy ước, và nó xói mòn im lặng — không test nào đỏ khi ai đó phá luật.

Code thật — eslint.config.mjs, luật chặn import sâu vào module khác:

const DEEP_IMPORT_INTO_MODULE = {
  // './modules/health/health.service'  ❌   nhưng './modules/health'  ✅
  regex: '(^|/)modules/[^/]+/.+',
  message: BOUNDARY_MESSAGE,
};
'no-restricted-imports': ['error', { patterns: [DEEP_IMPORT_INTO_MODULE] }],

Code thật — src/common/filters/all-exceptions.filter.ts, "một hình dạng lỗi" nhắc ở Technical, nhìn thấy ngay trong code chỉ 3 nhánh:

private describe(exception: unknown): { status: number; body: ErrorBody } {
  if (exception instanceof DomainError) {
    return { status: exception.httpStatus, body: { code: exception.code, message: exception.message } };
  }
  if (exception instanceof HttpException) {
    return { status: exception.getStatus(), body: { code: 'HTTP_ERROR', message: exception.message } };
  }
  // Lỗi lạ, chưa lường trước — vẫn phải trả về ĐÚNG hình dạng, không rò rỉ chi tiết nội bộ.
  return { status: 500, body: { code: 'INTERNAL_ERROR', message: 'Lỗi hệ thống...' } };
}
