Phase 2 — Product & Inventory

Hoàn tất theo Definition of Done — 28/28 integration + 43/43 unit test pass, seed 100.000 SKU đã chạy, bằng chứng EXPLAIN đã đo trên Postgres thật.

Business

Cần một catalog để user duyệt trước khi săn: mẫu áo + biến thể (size × màu). Tồn kho phải tính theo từng biến thể, không theo mẫu áo — "hết size M màu đen" là chuyện khác hẳn "hết mẫu áo".

Technical

  • CRUD Product + ProductSku — tồn kho gắn ở SKU, không phải ở Product.
  • Cursor (keyset) pagination — API GET /skus chịu tải 100.000 dòng mà không chậm dần theo độ sâu trang.
  • JSONB + GIN index cho thuộc tính mở (chất liệu, xuất xứ) — size/ màu vẫn là cột thật, có tập giá trị đóng.
  • CHECK constraint (stock >= 0) làm lưới an toàn cuối — Phase 2 cố tình chưa chống race condition thật, đó là việc của Phase 3.
  • Seed 100.000 dòng để đo hiệu năng trên dữ liệu thật, không phải suy đoán trên vài chục dòng.

Kiến thức học được (Q&A)

Số liệu dưới đây đo thật trên chính repo này (xem tech-playbook.md §Phase 2 để xem plan EXPLAIN đầy đủ), không phải ví dụ trong sách.

1. Cursor vs offset pagination khi dữ liệu lớn?

OFFSET N bắt Postgres đi qua index/bảng, đếm bỏ qua N dòng rồi mới lấy — chi phí tăng tuyến tính theo N. Keyset dùng WHERE (created_at, id) < (mốc) để index nhảy thẳng tới vị trí — chi phí gần như hằng số bất kể đang ở trang mấy. Số thật: cùng vị trí dòng 80.000/100.000, offset đọc 78.563 block/88ms, keyset đọc 22 block/1,8ms — cùng một index, khác nhau ở cách dùng. Đánh đổi: offset nhảy được tới trang bất kỳ (trang 47), keyset chỉ đi tuần tự tiếp/lùi từ một mốc — hợp kiểu cuộn vô hạn, không hợp UI có số trang bấm được.

2. GIN vs B-tree hợp cho loại truy vấn nào?

B-tree: mỗi dòng ứng với một giá trị trong cây — hợp =, <, >, BETWEEN, ORDER BY. GIN: hợp giá trị nhiều phần tử trong một ô (một key JSONB, một từ trong văn bản, một phần tử mảng) — mỗi phần tử trỏ ngược lại danh sách dòng chứa nó, giống mục lục cuối sách. Có GIN không có nghĩa nó luôn thắng: trên 10.000 dòng, Seq Scan (1,65ms) nhỉnh hơn cả truy vấn có GIN (1,92ms) — GIN phải tra cấu trúc RỒI đọc lại dòng thật (Recheck Cond), chỉ đáng giá khi việc đó giúp bỏ qua phần lớn dữ liệu.

3. Khi nào JSONB là lựa chọn tệ?

  • Cần ràng buộc tập giá trị đóng — JSONB không CHECK được nội dung bên trong (gõ nhầm DB vẫn nhận).
  • Cần join/filter cao tần trên đúng field đó — containment JSONB luôn tốn hơn so sánh bằng trên cột index thẳng, và không làm khoá ngoại được.
  • Bảng nhỏ hoặc field ít khi bị lọc — GIN có phí ghi (mỗi INSERT/UPDATE phải cập nhật cấu trúc index), trả phí đó mà ít khi query theo field ấy là lỗ.
  • Cần đổi cấu trúc dữ liệu về sau — không có migration tự động kiểu đổi kiểu cột, phải tự viết script backfill.

Code thật — src/modules/product/product.repository.ts, đúng câu keyset vừa giải thích ở câu hỏi #1 (Prisma không có row-value comparison thẳng nên viết lại bằng OR):

async listProducts(cursor: Cursor | undefined, limit: number) {
  return this.prisma.product.findMany({
    where: {
      status: { not: 'ARCHIVED' },
      ...(cursor && {
        OR: [
          { createdAt: { lt: cursor.createdAt } },
          { createdAt: cursor.createdAt, id: { lt: cursor.id } },
        ],
      }),
    },
    orderBy: [{ createdAt: 'desc' }, { id: 'desc' }],
    take: limit + 1, // lấy dư 1 dòng để biết còn trang sau hay không
  });
}
