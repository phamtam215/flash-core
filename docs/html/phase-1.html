Phase 1 — Auth & Security

Code + test xong (2026-08-27) — 14/14 test case pass, 21 unit + 12 integration. Chờ Tâm review & push.

Business

User cần đăng ký/đăng nhập để tham gia săn sale. Vì hệ thống này có tiền thật (mua hàng), phiên đăng nhập phải vừa an toàn (token bị đánh cắp phải phát hiện được) vừa tiện (không bắt đăng nhập lại liên tục giữa lúc đang thao tác nhanh để săn hàng).

Technical

  • Argon2id hash mật khẩu — không bao giờ lưu mật khẩu thô.
  • JWT access (15 phút) + refresh (7 ngày), dùng hai secret riêng — access hết hạn không thể đem đi giả làm refresh.
  • Cookie HttpOnly cho cả hai token — JavaScript không đọc được.
  • Refresh Token Rotation + reuse detection: mỗi refresh token chỉ dùng đúng một lần.
  • Rate limit đăng nhập qua Redis — đếm đúng khi chạy nhiều instance, không phải đếm trong RAM của từng process.

Kiến thức học được (Q&A)

Ba câu này là Definition of Done của phase (docs/SPEC.md). Đáp án dưới đây nhúng thẳng từ tech-playbook.md — nguồn kiến thức duy nhất của repo, sửa ở đó là trang này đổi theo.

1. Vì sao Argon2 tốt hơn bcrypt?

Bcrypt chỉ tốn CPU. GPU/ASIC chạy song song hàng triệu lần hash/giây nên bcrypt ngày càng rẻ để dò theo đà tiến của phần cứng. Argon2 (biến thể argon2id) là memory-hard: mỗi lần hash bắt buộc cấp một lượng RAM cố định (dự án dùng 19 MiB) — GPU nhiều lõi tính nhưng không nhiều RAM bằng, nên không song song hoá được kiểu bcrypt bị. argon2id còn trộn argon2i (chống side-channel) với argon2d (chống GPU). Đánh đổi: tốn RAM+CPU thật của server mỗi lần login — dưới flash sale, hàng nghìn lượt đăng nhập × 19 MiB là con số phải tính.

2. HttpOnly chống XSS thế nào, vì sao vẫn phải lo CSRF?

HttpOnly nói với browser: "JavaScript không được đọc cookie này". XSS chỉ đọc được những gì document.cookie cho phép, nên cờ này cắt hẳn con đường đó. Nhưng CSRF là chuyện khác: cookie được browser tự động gửi kèm mọi request tới đúng domain, kể cả request do một trang web khác âm thầm kích hoạt. HttpOnly không ngăn việc gửi, chỉ ngăn việc đọc — hai chuyện độc lập. Chặn CSRF cần SameSite hoặc CSRF token riêng.

3. Refresh Token Rotation phát hiện token bị đánh cắp ra sao?

Mỗi refresh token dùng được đúng một lần: dùng xong bị đánh dấu revokedAt, cấp token mới cùng familyId. Kẻ trộm dùng trước → chủ thật dùng lại token cũ sau → hệ thống thấy token đã thu hồi mà vẫn bị dùng ⇒ reuse detection → thu hồi cả family. Chủ thật dùng trước thì kẻ trộm dính bẫy đó. Dù ai dùng trước, lần thứ hai luôn lộ — đó là toàn bộ ý tưởng. Cái giá: cả hai bên bị đăng xuất, vì lúc đó không có cách nào biết ai là chủ thật.

Code thật — src/modules/auth/auth.service.ts, đúng nhánh reuse detection vừa giải thích ở trên:

if (stored.revokedAt) {
  // REUSE DETECTION: token đã bị vô hiệu mà vẫn có người dùng lại.
  const revokedCount = await this.repo.revokeFamily(stored.familyId);
  this.logger.warn(
    { userId: stored.userId, familyId: stored.familyId, revokedCount },
    'Phát hiện refresh token bị dùng lại — đã thu hồi toàn bộ family',
  );
  throw new InvalidRefreshTokenError();
}
