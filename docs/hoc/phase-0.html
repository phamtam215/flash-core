Phase 0 — Nền móng & ranh giới đã đóng 2026-08-08

Phase duy nhất không có tính năng nào cho người dùng. Nó quyết định sáu tháng nữa code này còn sửa được hay không — và đó là thứ đắt nhất trong mọi dự án.

Kết quả: 16/16 test · CI xanh từ máy sạch · 2 ADR · ESLint chặn import sâu · Code sinh ra: ~990 dòng.

Đoán thử trước khi đọc

Một dự án chia thư mục rất đẹp: modules/auth/, modules/order/, modules/product/. Nhưng trong order.service.ts có dòng import { AuthService } from '../auth/auth.service'.

Dự án đó có "ranh giới module" không? Trả lời trong đầu, rồi đọc tiếp.

Bài toán

Chủ dự án viết spec, AI viết code. Nghĩa là code sẽ được sinh ra nhanh hơn tốc độ đọc. Trong hoàn cảnh đó có đúng hai thứ giữ cho dự án không sụp:

1. Ranh giới do máy giữ, không do người nhớ

Quy ước "đừng import sâu vào module khác" sẽ bị phá — không phải vì ai đó cố tình, mà vì đến lần thứ n thì không ai nhớ. Và nó bị phá im lặng: không test nào đỏ. Muốn ranh giới tồn tại thật thì phải có máy chặn.

2. Sai cấu hình phải chết lúc khởi động

Thiếu một biến môi trường mà app vẫn lên được, thì nó sẽ chết lúc 3 giờ sáng, ở request đầu tiên chạm tới biến đó, với thông báo lỗi chẳng liên quan gì. Rẻ nhất là chết ngay lúc npm run dev.

Vì sao là Modular Monolith, không phải microservices

Đáp án cho câu đoán ở đầu trang

Không. Dự án đó không có ranh giới nào cả

Ranh giới module không do thư mục tạo ra, mà do import tạo ra. Chia thư mục đẹp mà import xuyên thẳng vào file bên trong module khác thì ranh giới bằng đúng số 0 — chỉ khác monolith thường ở chỗ nhìn có vẻ gọn gàng hơn.

Cách code — bốn quyết định, theo đúng thứ tự

① Cấu hình: một schema, chạy lúc boot

Luật của dự án: chỉ src/config/ được đọc process.env. Mọi nơi khác nhận object Env đã được Zod ép kiểu và kiểm tra.

// src/config/env.schema.ts (rút gọn)
const schema = z.object({
  NODE_ENV: z.enum(['development', 'test', 'production']).default('development'),
  PORT: z.coerce.number().int().positive().default(3000),
  DATABASE_URL: z.string().url(),
  JWT_ACCESS_SECRET: z.string().min(32),      // thiếu hoặc ngắn → app KHÔNG lên
  INVENTORY_STRATEGY: z.enum(['optimistic', 'pessimistic', 'redis']).default('optimistic'),
});

Cách sai

const port = process.env.PORT;   // string | undefined
app.listen(port);                // "3000" hay undefined?

Đọc rải rác, không ai kiểm. Sai thì lộ ra ở nơi khác, lúc khác.

Cách của dự án

const env = app.get<Env>(ENV);
await app.listen(env.PORT, '0.0.0.0');

env.PORT chắc chắn là số. Thiếu biến thì đã chết ở dòng NestFactory.create(), kèm tên biến bị thiếu.

② Thứ tự khởi động trong main.ts

③ Lỗi: controller chỉ throw, biên lo phần còn lại

service throw DomainError → controller không bắt → AllExceptionsFilter map sang HTTP → client { code, message, correlationId }

Filter đăng ký bằng APP_FILTER trong app.module.ts, nghĩa là không controller nào thoát được. Thêm một loại lỗi nghiệp vụ mới = tạo một class kế thừa DomainError, không phải sửa filter.

④ correlationId — 7 dòng, dùng suốt 8 phase

// src/common/logger/logger.module.ts
genReqId: (req, res) => {
  const incoming = req.headers['x-correlation-id'];
  const id = typeof incoming === 'string' && incoming.length > 0 ? incoming : randomUUID();
  res.setHeader('x-correlation-id', id);   // trả về cho client
  return id;                               // pino gắn vào MỌI dòng log của request này
}
Dòng "nếu client đã gửi thì dùng lại" quan trọng ngang dòng sinh id mới

Nếu mỗi thành phần tự sinh id riêng thì một hành động của khách để lại hai id khác nhau ở API và worker — nối lại không được, và cả cơ chế thành vô nghĩa. Phase 6 mở rộng đúng ý này ra khỏi biên HTTP bằng AsyncLocalStorage.

Cách test

Unit — npm test

File *.spec.ts nằm cạnh code nó test. Không cần Docker, chạy tính bằng mili giây. 11 test ở phase này: validateEnv (mặc định, ép kiểu, báo thiếu biến, từ chối enum sai), Zod pipe (parse đúng / 400 kèm tên field / loại field lạ), health service.

Integration — npm run test:int

File test/*.e2e-spec.ts, dựng Postgres 16 thật bằng Testcontainers. 5 test: /health 200, header x-correlation-id sinh mới, giữ nguyên id client gửi lên, /ready với DB thật, route lạ → 404 qua filter chung.

Câu hỏi chọn tầng test: rủi ro nằm ở đâu?

Rủi ro trong logic của mình → unit. Rủi ro nằm ở tương tác với thứ mình không viết (khoá của Postgres, thứ tự message của Redis, chữ ký webhook) → bắt buộc integration. Mock chỗ đó là tự lừa mình — và đó chính là lý do Phase 3 không thể dùng mock.

Phép thử cho bộ test (dùng được ở mọi phase): cố tình xoá một if trong code rồi chạy test. Không có test nào đỏ ⇒ vùng đó chưa được bảo vệ, bất kể coverage bao nhiêu. Coverage đếm dòng được chạy qua, không đếm dòng được kiểm chứng.

Vì sao "CI xanh" mới là tiêu chí, không phải "test xanh"

Máy của mình xanh chỉ chứng minh "chạy được với những thứ tình cờ đang có sẵn ở đây". CI là máy sạch: nó chứng minh "chạy được từ số 0, chỉ với những gì thật sự nằm trong git". Hệ quả trực tiếp: thứ gì code cần mà bị .gitignore thì CI phải sinh lại — ở đây là src/generated/prisma, nên bước npm run db:generate bắt buộc đứng trước typecheck.

Bị chỉ vào — trả lời thế nào

"Modular Monolith với Microservices khác nhau ở đâu?"

Cả hai là cách chia hệ thống, khác ở độ tách.

  • Monolith thường: một process, không ranh giới — nhanh viết, vài tháng sau thành mớ phụ thuộc chằng chịt.
  • Microservices: nhiều service tự deploy, tự DB — tách được thật, nhưng phải xây lại từ đầu mọi thứ mà một DB đơn lẻ vốn cho sẵn: distributed transaction, service discovery, độ trễ mạng.
  • Modular Monolith: một process, một DB, nhưng ranh giới module ép bằng máy — giữ được transaction và lock của một DB (đúng thứ Phase 3 cần), mà vẫn có sẵn "đường cắt" nếu sau này thật sự phải tách.
"Ranh giới module được ép bằng gì? Chứng minh đi."

Hai tầng, cả hai đều là máy chứ không phải quy ước:

  1. DI container của NestJS — provider không nằm trong exports thì module khác không inject được. Nhưng nó chỉ chặn inject, không chặn import thẳng file rồi tự new.
  2. ESLint no-restricted-imports — chặn đúng lỗ hổng đó.

Thiếu tầng 2 thì ranh giới xói mòn im lặng: không test nào đỏ khi ai đó phá luật. Chứng minh bằng cách thêm một dòng import { AuthService } from '../auth/auth.service' rồi chạy npm run lint.

"Vì sao import 'dotenv/config' phải là dòng import đầu tiên?"

JavaScript chạy hết mọi import theo đúng thứ tự viết, trước khi vào thân hàm. Dòng import { AppModule } kéo theo cả cây module, trong đó ConfigModule đọc process.env để validate. Nếu dotenv chưa chạy tại thời điểm đó thì process.env còn rỗng.

Triệu chứng khi đảo thứ tự: app báo "DATABASE_URL là bắt buộc" và chết lúc khởi động, dù file .env hoàn toàn đầy đủ. Loại lỗi tốn hàng giờ vì thông báo trỏ sai chỗ — nó nói "thiếu biến", nguyên nhân thật là "đọc quá sớm".

"Vì sao validate config lúc khởi động chứ không lúc dùng?"

Vì hai kiểu hỏng có giá khác hẳn nhau. Validate lúc boot: sai cấu hình thì app chết ngay khi npm run dev hoặc ngay khi container mới lên — người deploy thấy liền, chưa có khách nào bị ảnh hưởng. Validate lúc dùng: app lên bình thường, rồi chết vào 3 giờ sáng ở request đầu tiên chạm tới biến đó, với stack trace nằm ở tầng hoàn toàn khác.

Đây là lá chắn rẻ nhất của cả hệ thống: một schema, một chỗ, chạy một lần.

"Vì sao @Global() cho Prisma mà không cho module nghiệp vụ?"

@Global() nghĩa là "ai cũng dùng được mà không cần khai báo phụ thuộc". Đó là đánh đổi: tiện, nhưng làm mất thông tin về việc ai phụ thuộc ai.

Chấp nhận được cho hạ tầng vì có ràng buộc kỹ thuật thật: connection pool phải là một instance duy nhất cho cả app — nhiều pool là nhân số connection lên và cạn giới hạn của Postgres. Không chấp nhận cho nghiệp vụ, vì lúc đó nó chỉ là sự lười khai báo, và ranh giới module biến mất.

Lưu ý: PrismaService là @Global không có nghĩa được gọi Prisma ở mọi nơi — truy cập DB vẫn phải gom trong *.repository.ts của module.
