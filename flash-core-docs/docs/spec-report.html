Dự án Flash-Core v2

Săn Flash Sale Áo Thun — High-Performance E-commerce Engine

Định hướng: Backend Middle → Senior | Kiến trúc: Modular Monolith | Quy trình: AI-assisted, Human-controlled

1. Nguyên nhân & Động lực

Hầu hết pet project của Junior dừng ở mức CRUD. Flash-Core giải quyết các bài toán Production thật, và quan trọng hơn: chứng minh bằng số liệu đo được, không chỉ bằng lời mô tả.

  • Concurrency: 1.000 người cùng mua 10 sản phẩm — làm sao oversell = 0? Không chỉ làm 1 cách, mà so sánh 3 chiến lược và benchmark.
  • Async & Reliability: tác vụ nặng đẩy xuống Queue, có retry, có Dead Letter Queue, có Outbox pattern để không mất message.
  • Observability: hệ thống phải "kể" được nó đang làm gì — log có cấu trúc, correlation ID, metrics, health check.
  • FinOps: kiến trúc chuẩn Production (DB riêng, Cache riêng, Queue riêng) nhưng chi phí ~0đ nhờ free tier (GCP Cloud Run + Neon + Upstash).
  • AI-era Engineering: AI viết phần lớn code — con người viết spec, review, viết test, ra quyết định kiến trúc. Dự án này là nơi luyện đúng kỹ năng đó.

🎯 Mục tiêu: một "Masterpiece" mà mỗi dòng trên CV đều có bằng chứng kèm theo (benchmark report, test coverage, ADR, sơ đồ kiến trúc).

2. Ý tưởng Dự án

Flash-Core là hệ thống săn flash sale áo thun theo kiến trúc Modular Monolith: mỗi đợt sale mở đúng giờ, các mẫu áo hot giảm giá sâu với số lượng cực giới hạn theo từng biến thể size × màu (ví dụ: mẫu "Đà Nẵng Rider" size L đen chỉ còn 5 chiếc). Hàng nghìn người canh giờ cùng bấm "Săn ngay" — đúng kịch bản tạo ra tranh chấp dữ liệu gắt nhất. Luồng nghiệp vụ: đăng nhập → xem sự kiện sale với đếm ngược & tồn kho realtime → chọn size/màu, săn hàng → đơn Pending giữ chỗ 15 phút → thanh toán qua cổng sandbox (VNPay sandbox / Stripe test mode), webhook xác nhận thành Completed, quá hạn tự hủy và trả hàng về kho. Giá trị cốt lõi nằm ở Backend; FE tối giản do AI đảm nhiệm 100% chỉ để trực quan hóa (xem mục 6).

Auth & Security Module

Argon2, Access + Refresh Token (HttpOnly Cookie), Refresh Token Rotation chống token theft, Rate Limiting chống brute-force.

Product & Inventory Module

Áo thun với biến thể size (S–XXL) × màu lưu bằng JSONB + GIN index; tồn kho quản lý theo từng SKU biến thể — kho càng chia nhỏ, tranh chấp càng thực tế. Cursor pagination, đọc query plan bằng EXPLAIN ANALYZE.

Order & Concurrency Module ⭐

Trái tim dự án: 3 chiến lược chống oversell (Optimistic / Pessimistic / Redis atomic), Idempotency Key chống double-order, Snapshot Price, ACID transaction, isolation levels.

Async & Notification Module

BullMQ: gửi email, tự hủy đơn quá 15 phút chưa thanh toán (delayed job), retry exponential backoff, DLQ, Outbox pattern.

Observability Module

Pino structured logging, correlation ID xuyên suốt request → queue, /health & /ready endpoint, Prometheus metrics, graceful shutdown.

Load Testing & Evidence

Kịch bản k6 mô phỏng flash sale, báo cáo so sánh throughput / latency / error rate giữa các chiến lược locking. Đây là bằng chứng cho CV.

4. Quy trình làm việc với AI — "AI code, tôi control"

Đây là phần khác biệt lớn nhất so với pet project truyền thống. Vai trò của Tâm không phải là gõ code, mà là Kiến trúc sư kiêm Reviewer. Quy trình cho mỗi tính năng:

BướcAi làmNội dung
1. SpecTâmViết spec ngắn theo template: mục tiêu, input/output, edge cases, tiêu chí chấp nhận. Không có spec → không code.
2. Test caseTâm định nghĩa, AI viếtLiệt kê các test case phải pass (kể cả case ác ý: gọi API 2 lần cùng idempotency key, 100 request song song…). Test là hợp đồng.
3. ImplementAI (Claude Code)Code theo spec, tuân thủ CLAUDE.md của repo (convention, cấu trúc module).
4. ReviewTâmReview theo checklist: transaction boundary đúng chưa? lỗi nào bị nuốt? log đủ chưa? N+1 query? Quy tắc vàng: không merge code mà mình không giải thích lại được luồng chạy.
5. ADRTâmMỗi quyết định kiến trúc → 1 file ADR 5–10 dòng (bối cảnh, lựa chọn, trade-off). Cuối dự án có ~10 ADR = tài liệu phỏng vấn cực mạnh.
6. Tự kiểm traTâmTrả lời các "câu hỏi bản chất" của phase (xem lộ trình bên dưới) mà không nhìn code. Chưa trả lời được → chưa qua phase.

💡 Chính quy trình này (spec-driven, review checklist, ADR) là thứ Tâm có thể mang lên CV và cả seminar nội bộ: "cách kiểm soát chất lượng code do AI sinh ra".

5. Lộ trình 7 Phase (~10–12 tuần, mỗi tuần 3–4 buổi tối)

Phase 0 — Nền móng & Quy trình AI (1 tuần)

Repo + Docker Compose (Postgres, Redis) + NestJS skeleton + Prisma + CI (lint, test). Viết CLAUDE.md, template Spec/ADR, review checklist.

Deliverable docker compose up chạy được toàn bộ; CI xanh trên GitHub.

🧠 Câu hỏi bản chất: Modular Monolith khác Microservices chỗ nào? Vì sao dự án 1 người KHÔNG nên làm microservices? Ranh giới module được enforce bằng gì trong NestJS?

Phase 1 — Auth & Security (1–1.5 tuần)

Đăng ký/đăng nhập với Argon2, Access Token (15 phút) + Refresh Token (7 ngày) qua HttpOnly Cookie, Refresh Token Rotation, rate limiting login.

Deliverable Bộ integration test cho toàn bộ luồng auth, kể cả case token bị đánh cắp và reuse.

🧠 Vì sao Argon2 tốt hơn bcrypt? HttpOnly Cookie chống XSS thế nào, và vì sao vẫn phải lo CSRF? Refresh Token Rotation phát hiện token theft ra sao?

Phase 2 — Product & Inventory (1 tuần)

CRUD mẫu áo thun với biến thể size × màu (JSONB + GIN index), tồn kho theo từng SKU biến thể, cursor-based pagination, seed 100.000 SKU để thấy sự khác biệt của index.

Deliverable File so sánh EXPLAIN ANALYZE trước/sau khi đánh index.

🧠 Cursor pagination hơn offset ở điểm nào khi dữ liệu lớn? GIN index hoạt động khác B-tree ra sao? Khi nào JSONB là lựa chọn tệ?

Phase 3 — Order & Concurrency ⭐ (2–2.5 tuần — trái tim dự án)

Implement cả 3 chiến lược chống oversell, bật/tắt bằng config:

  • A. Optimistic Locking: cột version, update thất bại thì retry — hiểu vì sao phù hợp khi tranh chấp thấp.
  • B. Pessimistic Locking: SELECT ... FOR UPDATE qua $queryRaw — hiểu lock chờ nhau và nguy cơ deadlock.
  • C. Redis Atomic: trừ kho trên Redis bằng Lua script (atomic), ghi DB async — hiểu trade-off tốc độ vs độ bền dữ liệu.

Kèm: Idempotency Key cho API đặt hàng, Snapshot Price, transaction bọc đúng ranh giới.

Evidence cho CV Báo cáo k6: 1.000 VU cùng săn 100 chiếc áo của 1 mẫu hot (chia theo các SKU size/màu) — bảng so sánh throughput, p95 latency, tỷ lệ lỗi của A/B/C, và oversell = 0 ở cả ba.

🧠 Vì sao check-rồi-update (read → if → write) chắc chắn oversell dưới tải cao? Isolation level nào là mặc định của Postgres và nó cho phép anomaly gì? Nếu Redis chết sau khi trừ kho nhưng trước khi ghi DB thì xử lý sao?

Phase 4 — Async, Queue, Payment Webhook & Reliability (2 tuần)

BullMQ: gửi email xác nhận, delayed job tự hủy đơn quá 15 phút chưa thanh toán, retry exponential backoff, Dead Letter Queue. Nâng cấp: Outbox pattern — ghi event vào DB cùng transaction với đơn hàng, worker đọc outbox đẩy vào queue.

Tích hợp cổng thanh toán sandbox (VNPay sandbox hoặc Stripe test mode): verify chữ ký webhook, xử lý webhook idempotent (gateway gửi trùng nhiều lần), và case ác nhất — webhook "đã thanh toán" đến sau khi đơn đã bị tự hủy vì quá hạn.

Deliverable Demo "rút dây mạng": kill worker giữa chừng, chứng minh không mất message, không gửi email trùng.

🧠 At-least-once vs exactly-once — cái nào là thực tế đạt được? Vì sao consumer phải idempotent? Outbox pattern giải quyết vấn đề gì mà "ghi DB xong rồi push queue" không giải quyết được? Vì sao phải verify chữ ký webhook, và xử lý sao khi webhook thanh toán đến sau khi đơn đã bị hủy?

Phase 5 — Observability & Hardening (1 tuần)

Pino structured log (JSON), correlation ID chảy từ HTTP request xuống tận queue worker, endpoint /health & /ready, Prometheus metrics (orders_created_total, queue_depth…), graceful shutdown (đóng server → chờ job xong → đóng DB).

Deliverable Từ 1 request lỗi bất kỳ, truy được toàn bộ hành trình của nó qua log chỉ bằng 1 correlation ID.

🧠 /health khác /ready thế nào và Cloud Run dùng chúng ra sao? Graceful shutdown sai thì mất gì? Log thế nào để vừa debug được vừa không lộ dữ liệu nhạy cảm?

Phase 6 — Deploy, FinOps & Đóng gói CV (1–1.5 tuần)

Deploy Cloud Run (free tier) + Neon Postgres + Upstash Redis, GitHub Actions tự động deploy khi merge main, secret qua Secret Manager. Hoàn thiện README: sơ đồ kiến trúc, hướng dẫn chạy 1 lệnh, link báo cáo benchmark, danh mục ADR.

Evidence cho CV API live trên internet + repo public với README chuẩn "đọc 3 phút hiểu toàn bộ hệ thống".

🧠 Cold start của Cloud Run ảnh hưởng gì đến flash sale và min-instances giải quyết ra sao? Connection pooling với serverless (Neon pooler) khác gì server truyền thống? Chi phí sẽ phát sinh ở đâu đầu tiên nếu traffic thật tăng?

6. Frontend — Công cụ trực quan, AI làm 100%

FE trong dự án này không phải sản phẩm, mà là công cụ trực quan hóa Backend. Toàn bộ code FE do AI (Claude) đảm nhiệm; vai trò của Tâm chỉ là viết spec 1 trang và giữ kỷ luật scope.

Hạng mụcQuy định
Scope — 4 màn hình(1) Đăng nhập / Đăng ký. (2) Trang sự kiện sale: lưới mẫu áo, đồng hồ đếm ngược giờ mở bán, tồn kho realtime theo từng size/màu. (3) Chọn size/màu + nút "Săn ngay" → trạng thái đơn: giữ chỗ 15 phút đếm ngược, nút thanh toán qua sandbox gateway. (4) Đơn của tôi: Pending / Completed / Cancelled.
TechVite + React + Tailwind. Tồn kho realtime bằng polling 1–2 giây (đủ dùng, đơn giản); nâng cấp SSE nếu còn thời gian trong timebox.
TimeboxTối đa 2 buổi tối, làm ở Phase 3 (khi đã có API thật). Quá timebox → cắt còn màn hình (2) và (3). Trước đó dùng Swagger UI thay FE.
Miễn trừ quy trìnhFE không cần test, không ADR, không tính coverage, không review kỹ như BE. Chỉ cần chạy được và hiển thị đúng dữ liệu.
Vai trò evidenceCảnh quay đắt giá nhất của dự án: chạy k6 1.000 VU trong khi màn hình FE hiển thị tồn kho từng SKU rơi dần về 0 và dừng đúng ở 0 — 10 giây thuyết phục hơn cả trang báo cáo.

  • ✅ Test coverage ≥ 70% cho các module core (Order, Inventory), integration test chạy trên DB thật.
  • ✅ ~10 file ADR ghi lại các quyết định kiến trúc và trade-off.
  • ✅ Sơ đồ kiến trúc + sequence diagram cho luồng đặt hàng.
  • ✅ API đang chạy live trên Cloud Run, deploy tự động qua CI/CD.
  • ✅ Tích hợp cổng thanh toán sandbox với webhook được verify chữ ký và xử lý idempotent — có test cho case webhook trùng và webhook đến muộn.
